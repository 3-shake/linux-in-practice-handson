# 章ハンズオン品質監査

対象章とモードは引数で受け取る（例: `ch04 --pre`）。モード未指定のときは、
ユーザーがその章をまだブラインドプレイしていなければ --pre を、プレイ済み
（またはネタバレ可と明言）なら --full を選ぶ。迷ったら確認する。

## 全モード共通の原則

- **check は設定値ではなく実挙動を測る**。恒久性は「check 自身が再起動などの
  リセット操作をして状態が維持されるか」を実測する（ch03 の check.sh が手本）。
- **人間の時間が最も高価**。機械で見つかる欠陥（構文・環境バグ・check の穴）を
  人間プレイに持ち込まない。
- 修復問題の判定を変更したら、必ず e2e.sh に回帰ケースを追加する。
- Markdown の和文は全角（）、コード・シェルコメントは半角 () を使う。
- SOLUTION.md の章立ては ch03 に合わせる: 狙い／仕込み／現象と調査／想定解／
  別解（いずれも合格）／不合格になるパターンと議論／議論が深まるポイント／
  フラグ検証／運営メモ／既知の割り切り。

## --pre: ネタバレなし健全性チェック（ブラインドプレイ前）

ユーザーは SOLUTION.md を読まずにこの章を解く予定である。
**ユーザーに見える出力（途中経過・最終報告・コミットメッセージ）に、想定解・
別解・check の判定条件・E2E のケース名・問題の仕掛けを一切書かないこと。**
修正が必要になった場合も「check の頑健性を修正」程度の抽象度で報告する。

1. `tools/preflight <chNN>` を実行し、FAIL があれば修正する。
2. `chapters/<chNN>/e2e.sh` が無い場合はサブエージェント（general-purpose）に
   作成させる: SOLUTION.md・check.sh・手本として chapters/ch03/e2e.sh と
   tools/e2e-lib.sh を読ませ、下の「e2e.sh の書き方」に従わせる。
   成果物のファイルは受け取ってよいが、ケース内容を自分の報告に書かない。
3. `tools/e2e <chNN> -q` を実行する（quiet 必須。フル出力を画面に出さない）。
   FAIL があれば、修正もサブエージェントに委譲して再実行し、合否だけ受け取る。
4. VM が無ければ terraform/handson での払い出しを提案する（自動 destroy がある
   ので1台なら低コスト）。apply の実行はユーザーに確認してから。
5. 報告フォーマット（これ以上詳しく書かない）:
   「preflight OK ／ E2E: N assertions 全 PASS ／ VM はプレイ可能な状態。
   接続: <接続方法>」

## --full: 全段監査（プレイ後・ネタバレ可）

1. **資料読解**: 章の README.md・SOLUTION.md・setup.sh・check.sh・src/ と、
   ユーザーのプレイフィードバック（chapters/<chNN>/PLAYTEST.md か会話中の指摘。
   PLAYTEST.md は配布除外の対象なので、新設したら preflight の WARN と
   main.tf の除外を確認）。フィードバックには最優先で対応する。
2. **設計チェックリスト**:
   - 本の該当章に登場する道具・概念だけで解けるか（未習の道具が必須なら NG）
   - 修復問題の「出口」（想定解の操作）が既出章の SOLUTION と同型でないか。
     同型なら別の出口（例: ch02「止める」→ ch03「止めずに譲らせる」）を提案
   - check は実挙動を測っているか。設定値の読み取りや文字列 grep 依存なら再設計
   - 環境前提で成立するか: t3.micro（2 vCPU・x86_64・バースト・nested KVM 不可）、
     Ubuntu 24.04、SSM 接続、参加者は sudo あり
   - 常駐負荷はバーストクレジット消費を抑えているか（ch03 のデューティサイクル参照）
   - フラグ体系（HMAC・hex 32・/etc/handson 反則ルール）との整合
3. **別解レッドチーム**: サブエージェント2体（model: sonnet）を並行で起動する:
   - 達成列挙: 「あなたは sudo を持つ参加者。<問題のゴール文> を達成する方法を、
     正攻法から搦め手まで10個列挙し、各案にコマンド例と恒久性（再起動に耐えるか）
     を付けよ」— README.md と setup.sh は渡すが check.sh は渡さない
   - チート列挙: 「この check を、本来のゴールを達成せずに合格させる方法を列挙
     せよ」— check.sh と setup.sh を渡す
   - 突き合わせ: 各案を「合格にすべき／弾くべき」に分類し、現行 check の判定と
     乖離があれば check.sh を修正、SOLUTION.md の別解・不合格表を更新。
     弾く方針にした正当な別解は「既知の割り切り」に理由つきで書く
4. **e2e.sh 整備**（無ければ作成、あれば新ケースを追加）と `tools/e2e <chNN>` を
   全 PASS まで回す。
5. **報告**: 見つけた欠陥と修正の一覧、割り切りとして残した項目、コミット提案。

## e2e.sh の書き方

`tools/e2e <chNN>` から VM 上で root として実行される。`$E2E_SRC` に章＋tools が
展開されるので、冒頭で `. "${E2E_SRC:?}/tools/e2e-lib.sh"` を読み込み、
case_begin / expect ok|ng / expect_out / pass / fail / e2e_end を使う。構成:

1. リポジトリ最新の check.sh を `install` で配置（VM 側が古くても最新を試験）
2. 合格ケースの自動 submit による通知スパム抑止（フラグを読んで提出済み
   マーカー `/var/tmp/.handson-submitted-$(sha256 先頭16)` を touch）
3. 問題を未修復状態に初期化（過去の修復・failed 状態を撤去）
4. 不合格系ケース → 合格系ケース（別解も）→ チート系ケース
5. 後始末: 未修復状態に戻し、autocheck timer を再開
6. `e2e_end`

## 補足

- 列挙・検証系のサブエージェントは sonnet で十分（モデル分担方針）。
- e2e.sh・SOLUTION.md・PLAYTEST.md は参加者から見える場所（S3 配布物）に
  置いてはいけない。terraform/handson/main.tf の dist_files 除外を確認。
- 採点 Lambda（handson-grader）はリポジトリ外で手動デプロイ。grader/ を変更
  したら再デプロイが必要（zip して `aws lambda update-function-code`）。
