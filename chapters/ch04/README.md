# 第4章 メモリ管理システム — ハンズオン

対象範囲: free/sar によるメモリ情報の取得、OOM killer、仮想記憶、mmap() システムコール、
デマンドページング(仮想メモリの確保と物理メモリの割り当ての違い)、ページテーブル、
/proc/<pid>/maps によるメモリマップの観察

ルール:

- VM の中では何をしてもかまいません(man、Web 検索も自由)
- ただし `/etc/handson/` 以下を直接読むのは反則です(修正タスクの答え合わせ用)
- フラグは `flag{...}` の形式です。取得したら VM 上で `submit 'flag{...}'` を実行してください
  (採点サーバーがあるときは正解すると Slack に自動でお祝いが流れます。
  ないときはその場でローカル採点されます)

## 問題1(CTF): 生きているプロセスのメモリ

`ch04-keeper` というプログラムがバックグラウンドで常駐しています。
このプログラムはあなた専用のフラグを計算しますが、**画面には表示せず、自分のメモリ上に
しまい込んだまま**動きつづけます。

```
$ sudo systemctl status ch04-keeper
...
ch04-keeper 稼働中 (pid=1234)。結果は自分のメモリ上に保管しました。
```

実行ファイルを `strings` で覗いてもフラグは出てきません(フラグはメモリ上にしか無いからです)。
このプロセスが**仮想アドレス空間のどこにフラグを置いているか**を突き止め、
**そのメモリの中身**を取り出してフラグを回収してください。

> ヒント: 4章「仮想記憶」「mmap() システムコール」「ページテーブル」。
> `/proc/<pid>/maps` の各行は 1 つのメモリ領域に対応します。怪しい無名領域はどれ?
> `ps` で VSZ(仮想メモリ量)と RSS(物理メモリ量)を比べると、デマンドページングの
> 気配が見えます。狙った領域の中身を丸ごと取り出す方法(コアダンプ等)を考えましょう。
> 取り出したダンプはただのファイルです。実行ファイルを覗いたのと同じ道具が
> そのまま使えます。

## 問題2(修正): OOM で死につづけるサービス

`ch04-app` というサービスが登録されていますが、起動しては死ぬのを繰り返しています。

```
$ systemctl status ch04-app
     Active: activating (auto-restart) (Result: oom-kill) ...
$ sudo dmesg | grep -i oom
... Memory cgroup out of memory: Killed process ... (python3) ...
```

本来 `ch04-app` は必要なメモリを確保して正常稼働に入るはずです。原因を調査し、
**恒久的に**修復してください。
修復できると **30秒以内に自動で判定されて通知が届き、フラグも自動提出されます**。
待ちきれないときや途中経過を見たいときは手動でも判定できます。

```
$ sudo ch04-check
```

> 注意: 判定はサービスをクリーンに再起動して行います。
> その場で手動実行して一度だけ通す方法では合格になりません(恒久修復が必要)。
> ヒント: 4章「OOM killer」「プロセスの削除によるメモリの強制回収」。
> なぜ殺される? このワーカーは実際どれだけメモリを使う?(`ps aux` の RSS)
> そして、どこで上限がかけられている?(`systemctl show ch04-app -p MemoryMax`)
